#
# Both arms fork James's coupled template and hold every training knob at his
# values (atmosphere frozen, 8 epochs, lr 7e-5, batch 8, n_ensemble 2, ocean
# EnsembleLoss CRPS 0.9 + energy 0.1). The ONLY change is stepper_training:
# the ocean's optimisation depth is sampled from the long-tail schedule
# (mean 7.50) under optimize_last_step_only, instead of a fixed 4.
#
# ocean codes (unchanged from ../coupled/pretraining.txt):
# - owc  = ocean_wide_ohc_clip rs2      (pjxiw906) -- crps4's init
# - owc8 = ocean_wide_ohc_clip-ft rs2   (pxz4q8hw) -- crps8's init
# atmos code: a2s = atmos_ace2s (j0ng1tw3), frozen, loss_weight 0
#
# Both checkpoints are James's own, so these arms carry his sea_surface_fraction
# masking (ace f00e06f70) -- unlike our MAE/stochastic arms, they ARE clean
# one-variable forks of crps4 / crps8.
#
# Cluster: 8 H100s on jupiter, not 4 B200s on titan. fp32 throughput (AMP is
# off in this recipe) makes 8xH100 ~26% faster per batch than 4xB200 here, and
# titan is budget-contended; measured in
# experiments/2026-09-10-coupled-ft-stochastic-and-mae.
#
# MEMORY PROBE, 2026-09-15. This wave first ran at cap 20 and both arms OOM'd
# in the first validation. Cause: memory scales with the CAP, not the sampled
# depth -- the frozen atmosphere's window (n_coupled_steps*20+1 timesteps) is
# retained and scored on every batch. ace#1496 (on this branch) removes three
# whole-window copies, cutting the per-atmosphere-timestep term 52%.
#
# Measured peaks, for anchoring: crps4 cghk183p cap4 85.2 GiB and crps8
# o0nc2dp3 cap8 148.2 GiB (both 4xB200, 2 samples/GPU) give 0.79 GiB per
# atmosphere timestep on a ~21 GiB base. On 8xH100 at 1 sample/GPU the slope
# halves, but the BASE is arm-specific and unexplained: mae2n 8chmcf8l implies
# 18.0 GiB, owc8v4 jc8l3r1d implies 40.2 GiB.
#
# PROJECTION for cap 16 on 8xH100 post-#1496: ~79.0 GiB against 79.6 available
# under the optimistic 18.0 GiB base -- i.e. expected to be marginal or to fail.
# Cap 12 projects to ~63.8 GiB (80%). This row is launched deliberately as a
# probe of that projection and of whether owc8v4's 40.2 GiB base is a glitch:
# RETRIES 0, one arm only. If it OOMs near 79 GiB the model is right and the
# fallback is cap 12 (or cap 16 on 4xB200, projected 143 GiB / 80%).

# --- owclt: crps4's ocean init, long-tail coupled schedule ---
# Pairs with crps4 (cghk183p): same init, schedule is the only change.
#
# 8xH100 on jupiter, after the 4xB200/titan launch (01M2M7M3VB8ZVS2QTX10SJ092G)
# was killed three times and cancelled. That failure was NOT GPU memory: the
# B200s peaked at 154.7 GiB of 179 (86.4%) and no attempt ever raised
# torch.OutOfMemoryError. Every death was the HOST OOM killer (torchrun root
# cause `exitcode: -9`), with node memory at 92.6 / 93.1 / 95.7%; the middle
# attempt instead hung rank 0 for 30 min in the inference aggregators and died
# on a NCCL watchdog timeout. Two causes, both set by the GPU count:
#   1. batch_size is a GLOBAL batch, so 4 ranks means 2 samples/GPU against
#      8 ranks' 1 -- per-rank host RSS measured ~300 GiB vs ~158 GiB.
#   2. 4 of 8 GPUs is a HALF-NODE claim (138/276 CPUs, 840 GiB shm on a
#      2101 GiB node), so the job shares host RAM with a co-tenant. The 8-GPU
#      twin owns its jupiter node outright (180/180 CPUs, 1868 GiB, 1494 GiB
#      shm) and has never exceeded 83.4% node memory.
# So GPU count is a lever on host RAM in the SAME direction as on GPU memory,
# and 8xH100 fixes both. The generated train-config.yaml is unchanged, so this
# stays a byte-identical fork of the owc8lt arm; only cluster and n_gpus move.
#
# Accepted exposure: at cap 16 on 8xH100 this will sit where owc8lt sits --
# ~99% of 79.6 GiB, revisiting that peak at each epoch's inline 20-yr rollout.
# That is the risk elynn already took deliberately for owc8lt; retries 3 (not
# owc8lt's probe-time 0) so a transient loss does not forfeit the run.
