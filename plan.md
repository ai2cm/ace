# Overview

Currently the Corrector in ace is responsible for diagnosing derived output values used in the loss, because no dedicated pathway existed for doing so. This leads to strange behaviors like having neural network output channels that are ignored (e.g. advection of moisture), and other outputs that are interpreted as something other than what they are (e.g. hfds network output being its value under sea ice but final value being hfds over the full gridcell). This makes the code significantly more confusing to think about, leading to complex consequences for example when thinking about pre-corrector optimization and corrector regularization.

Let's talk specifically about surface precipitation. In our critical path model, the corrector uses the network output for PRATEsfc in combination with the water budget defined by each other moisture field, and determines the magnitude needed for PRATEsfc to close the water budget. In other words, the network output is really the pattern of precipitation, and the corrector is responsible for deriving the final value of PRATEsfc. Afterwards, the corrector also clips PRATEsfc so it is strictly positive - this is a correction applied to the predicted PRATEsfc value.

Currently, there is no way to distinguish between these two actions applied to PRATEsfc. They both appear as a "delta", and it is not possible for example to regularize the magnitude of predicted negative precipitation without also regularizing the "derivation" of PRATEsfc. Applying pre-corrector optimization on the zero clipping may (or may not) make sense, but is straightforward to conceptualize, and whether it makes sense is independent of whether it makes sense for the derivation of PRATEsfc (the effect of which is significantly more challenging to reason about). Currently it is not possible to try potentially-helpful configurations that involve only reverting one or the other of these effects when applying pre-correction and corrector regularization.

In a sense, the code currently lies about the neural network output being PRATEsfc, which can confuse external users into thinking this output is meant to represent the physical field the code says it represents (e.g. Chapman et al. 2026 https://arxiv.org/pdf/2607.18416). In this plan, we address these issues by updating the presentation to match what the code is doing. This has a secondary benefit of making it easier to reason about corrector regularization and pre-corrector optimization - it should be scientifically valid to "apply corrector regularization to all corrected fields", but it currently is not. This would be one step in that direction.

If we later decided the network output should in fact be PRATEsfc and not just its relative pattern, the code would be updated accordingly so that it continues to reflect what our model actually does.

# Plan

We’d like to decouple these responsibilities by formalizing two classes of output variables:
- Values computed by the Module, but which are never optimized in the loss (computed-unoptimized, in this draft).
- Values which are derived from Module-output values, and are optimized in the loss (derived-optimized, in this draft).

Certain corrector features treat these two values as one identical value, with overwriting.

This first slice will target one such feature - precipitation in the context of global-mean moisture conservation - to prove out the code framework. It will introduce a field `PRATEsfc_relative_pattern` which is output by the neural network when this type of correction is enabled, has no target data, will not be optimized in the loss. It should be reported in aggregators in the way any other derived value without target data is reported. `PRATEsfc` itself will be a value derived from this value, which is directly optimized in the loss despite not being a NN output. Because of this, there will be no corrector "delta" assigned to PRATEsfc - it is derived, not corrected. In this pass, the responsibility for deriving PRATEsfc will remain in the corrector. Any renaming of the corrector or other refactoring to make this clearer is left for future work.

Any information owned by `ATMOSPHERE_FIELD_NAME_PREFIXES` or related name mappings will not be duplicated by the corrector. If that information needs to be used for this feature, it will be referenced in the place where it is currently owned, rather than duplicated, for example potentially with a `get_precipitation_name(candidate_names)` function on AtmosphereData.

The function `_force_conserve_moisture`, which currently directly calls `gen.set_precipitation_rate`, currently owns the mapping from what correction is being used to whether precipitation is being derived. This helper method is only called by MoistureBudgetCorrection, which is the true owner of this choice - the private function only exists because of organic growth of the code, and will be moved to a class method on MoistureBudgetCorrection. MoistureBudgetCorrection will provide a metadata attribute containing `{"PRATEsfc": "PRATEsfc_relative_pattern"}` as a mapping of replacement network output names when the correction is enabled, and an empty mapping otherwise. That class would also own any normalization concerns related to this feature (by providing a method or exposing an attribute, so that PRATEsfc_relative_pattern uses the normalization constants for PRATEsfc). The corrector will then use this metadata, but not own it.

Currently, the corrector zero-clips the pattern field and then rescales it. With this refactor, it will be necessary to compute the derived PRATEsfc at the same time as zero clipping it, returning the delta that corresponds only to the zero clipping, since the magnitude of the rescaling depends on whether precipitation is being zero-clipped. Another option would be to zero clip the pattern field, but we need this clipped amount to be in precipitation units, not in relative units, so that corrector regularization doesn't just encourage the pattern to have arbitrarily small magnitude. We may go this route by clipping the pre-rescaling field and then rescaling the delta to precipitation units - this still requires we perform both operations in the same scope to make sure they're correctly aligned.

# Lifecycle: How is PRATEsfc_relative_pattern created, tracked, and linked to PRATEsfc?

During corrector initialization, `MoistureBudgetCorrection`, or a new configuration-only class tied to it, is initialized with a flag `terms_to_modify: "advection_and_precipitation"`. This exposes a metadata attribute `{"PRATEsfc": "PRATEsfc_relative_pattern"}`. SingleModuleStepConfig will rely on `self.corrector.get_module_output_names(output_names)` to determine the correct network output names to use for the model, and `self.corrector.wrap_module_output_normalizer(normalizer)` to update normalization. This will be backwards-compatible - the existing PRATEsfc channel will be renamed in-place. Module output names not already present in output_names will be added to the publicly-exposed list of StepABC `output_names`, but not to the `loss_names`. This closes all API contracts at that stage - no further changes are needed above the SingleModuleStep level.

# Separation of concerns

This concern will live in the Corrector and SingleModuleStep. A level within the Corrector will own all involved field names, exposing lists of field names as needed upwards to the Step (e.g. so it can construct its own name lists, and including the output Packer). Objects above the Step shouldn’t require any changes. This name ownership and propagation should be done in its own PR, creating the framework that allows the Corrector in theory to define derived fields, without actually defining one, before defining the PRATEsfc derived field in its own, separately reviewable PR.

The Step will need to use a modified normalizer/scaler to allow it to use the Corrector’s specification of how to normalize pre-derived fields. In the future, for example, we may want fields to be 0-1 scaled explicitly (e.g. this _would_ be the case for PRATEsfc_relative_pattern, except that we care about backwards compatibility at this stage). We will ensure the Corrector owns these details by providing a `wrap_module_output_normalizer` method the Step applies to its normalizer. This ensures the normalization library code itself doesn’t need to worry about Corrector concerns.
